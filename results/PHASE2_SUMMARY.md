## Round 2 — 12-Feature Expansion

Expanded the candidate representation from 6 to 12 features per reviewer
feedback. Split the pipeline so `data_processing/candidate_gen.py` now only
generates raw candidates + the 6 base geometric features (unchanged), and
`feature_engineering/extract_features.py` is the new module that adds the 6
kinematic/derived features and builds the final train/test tables:

1. `perp_dist`, 2. `proj_ratio`, 3. `heading_error`, 4. `heading_cos`
   (`cos(radians(heading_error))`), 5. `arc_length`, 6. `dist_to_start`,
   7. `dist_to_end`, 8. `speed_mps` (displacement between consecutive GPS
   points / `max(delta_t, 0.1s)`), 9. `delta_t`, 10. `candidate_rank`,
   11. `dist_diff_endpoints` (`abs(dist_to_start - dist_to_end)`),
   12. `traversal_time_est` (`arc_length / max(speed_mps, 0.5 m/s)`).

`candidate_rank`'s range was also bumped from 0–4 (k=5) to 0–9 (k=10):
the HMM tuning in round 1 found k=10 gave a meaningfully higher continuity
ceiling, so this was kept consistent across both the classifier and the
decoder's candidate sets. `hmm_viterbi/viterbi.py` now imports
`extract_features_for_trip` from the new module (instead of calling
candidate generation directly), guaranteeing training/inference feature
parity by construction.

Regenerated datasets: 2,084,170 rows / 80 trips (train), 191,600 rows / 10
trips (test), zero NaNs. **Note**: at 12 features × k=10 candidates,
`results/train_features.csv` is 208MB — over GitHub's 100MB hard push limit.
It is excluded via `.gitignore` and regenerated by
`feature_engineering/extract_features.py` (see README); `test_features.csv`
(18MB) stays committed since it's small and useful for reproducing evaluation
numbers directly.

### 5-model benchmark: 6 vs 12 features (full 80-trip dataset)

| Model | CV Macro F1 (6-feat) | CV Macro F1 (12-feat) |
|---|---|---|
| Logistic Regression | 0.7562 | 0.7444 |
| Distance-Weighted k-NN | 0.7697 | 0.7526 |
| Random Forest | 0.7905 | 0.7856 |
| HistGradientBoosting | 0.7879 | 0.7908 |
| **MLP (champion both rounds)** | 0.7984 | **0.7952** |

The extra features did **not** uniformly improve CV Macro F1 — most models
moved slightly down, HistGradientBoosting moved slightly up. This is a
believable result, not a red flag: several of the 12 features are
derived/correlated with the base 6 (`heading_cos` from `heading_error`,
`dist_diff_endpoints` from `dist_to_start`/`dist_to_end`,
`traversal_time_est` from `arc_length`/`speed_mps`), so models sensitive to
added noise or collinearity (Logistic Regression, k-NN, Random Forest) can
see CV F1 dip slightly even as held-out discrimination improves elsewhere —
which is exactly what shows up downstream in the tuned model's held-out
Top-1 Accuracy (below). MLP remains champion by CV F1 in both rounds, but its
lead over HistGradientBoosting narrowed further (0.0105 → 0.0044 gap), while
its fit time *grew* relative to HGB (112.8s vs 5.21s on the 12-feature
dataset, a ~21.6x gap, up from ~19.3x at 6 features) — reinforcing the choice
below to tune HistGradientBoosting rather than the nominal champion.

## Task: Bayesian Hyperparameter Optimisation (Optuna) — 12-feature

**Model tuned: HistGradientBoosting**, again not the nominal champion MLP,
for the same practicality reason as round 1 (now an even larger speed gap).

- Search space: `learning_rate` (log-uniform, 1e-3–3e-1), `max_depth` (3–14),
  `max_leaf_nodes` (15–127), `l2_regularization` (log-uniform, 1e-4–1e-1),
  `min_samples_leaf` (10–200).
- Objective: maximize CV Macro F1 under `GroupKFold(n_splits=3, groups=trip_id)`.
- 30 trials, Optuna `TPESampler(seed=42)`. Search wall time: 835s.
- Best params: `learning_rate=0.0894, max_depth=13, max_leaf_nodes=84, l2_regularization=0.0232, min_samples_leaf=116`.

| Variant | CV Macro F1 | Student-Test Top-1 Accuracy | Log Loss |
|---|---|---|---|
| HistGradientBoosting (untuned, 12-feat) | 0.7908 | 73.09% | 0.4117 |
| **HistGradientBoosting (tuned, 30 trials, 12-feat)** | **0.7970** | **84.99%** | 0.4719 |
| *(for reference) tuned, 6-feat, round 1* | *0.7889* | *82.69%* | *0.4699* |

The 12-feature tuned model edges out the 6-feature tuned model on held-out
Top-1 Accuracy (84.99% vs 82.69%) — the kinematic features (`speed_mps`,
`delta_t`, `traversal_time_est`) add real discriminative signal once the
model is tuned to use them, even though they didn't help every model's raw
CV F1. Full trial log: `results/optuna_trials.csv`. Best params:
`results/optuna_best_params.json`. Tuned artifact: `results/best_tuned_model.joblib`.

## Round 3 — Production Polish & Visualization Artifacts

### Folium map component (`visualisations/folium_map.py`)
- Added the previously-missing grey road-network layer (the docstring
  claimed 4 layers but only 3 were implemented).
- Auto-fit zoom via `m.fit_bounds(...)` from the trip's GPS bounding box.
- Floating HTML/CSS legend (top-right, fixed position, visible regardless of
  which layers are toggled).
- Hover tooltips on GPS points showing observation index, time, and speed
  (computed from consecutive-point displacement, same method as
  `extract_features.py`'s kinematics).
- **Performance fix**: the first version rendered the grey network as one
  `folium.PolyLine` per arc and every raw GPS point as an individual
  `CircleMarker` with no cap. On a dense trip (`00000076`, 56,027 arcs in its
  `.arcs` file) this produced a **25MB single-trip HTML file** and 86MB
  across the 10 student-test maps. Rewrote the grey layer as one
  multi-segment `PolyLine` (single DOM element, capped at 4000 sampled
  arcs) and capped GPS markers to 500 (evenly subsampled) — brought the
  total down to **7.2MB across all 10 maps**, consistent with the Folium
  Map-Generation deliverable while staying practical to open in a browser
  or commit to the repo.

### Batch map generator (`visualisations/generate_production_artifacts.py`)
Runs the tuned model + HMM/Viterbi decoder across all 10 student-test trips
and exports standalone interactive HTML maps to `results/maps/` (no Python
needed to open them — evaluators can open directly in any browser).

### Diagnostic plots (`model_evaluation/generate_diagnostic_plots.py`)

- `results/plots/tuned_vs_untuned_comparison.png` — untuned vs tuned

- `results/plots/hmm_continuity_gain.png` — per-trip grouped bar chart,

### UI (`ui/app.py`)
- Added a "⬇️ Download Interactive HTML Map" button (`st.download_button`)
  so the evaluator can save the live-rendered map from Laptop 2.
- Added a status line confirming HMM/Viterbi decoding completed, with the
  reconstructed arc count.
- **Fixed a pre-existing schema bug** while touching this code: the UI read

## Round 4 — Integration fix, accuracy improvements, evaluator_test plumbing

**Resolved:** the `api/utils.py` silent 6-feature fallback was removed; the API now delegates to
`hmm_viterbi.viterbi.reconstruct_route` (verified over live HTTP).

**Corrected:** the earlier "untuned 73.09% -> tuned 84.99% (+11.9pp)" claim mixed a 5-fold CV number
with a student-test number. On a like-for-like student-test comparison, tuning gave +0.11pp Top-1
(84.88% -> 84.99%) and a flat log loss. README/report/CSV/PDF were corrected.

**Added:**
- `hmm_viterbi/viterbi.py`: deterministic post-Viterbi connectivity repair (`repair_route_gaps`):
  mean continuity 90.44% (HMM alone) -> 99.01%; 1,639 gaps bridged, 64 unrepairable (beyond the 400m
  cutoff, left as-is). Per-point assignments are untouched, so accuracy metrics are unaffected.
  A first version of this change computed pointwise accuracy over the longer repaired sequence
  (bridge arcs counted as predictions) and dropped it to ~0.38-0.86; fixed by keeping
  `predicted_arc_ids` per-timestep and exposing the connected route as `repaired_route_arc_ids`.
- `hmm_viterbi/tune_hmm_params.py`: 4x5 sigma/beta grid on student_test; selected sigma=25, beta=50
  (flat surface: 86.9%-88.9% pointwise accuracy across all 20 settings).
- `model_training/calibrate_model.py`: isotonic calibration experiment (group-aware); better log
  loss/Brier but no accuracy gain and an 88MB artifact, so not adopted.
- `api/utils.py`: `evaluator_test` is checked before `student_test` for trip discovery/lookup.
  Only status/JSON-shape was verified on an evaluator trip; no evaluator metric was inspected or used.
